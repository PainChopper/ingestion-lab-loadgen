# План телеметрии Sender

## Цель

Сделать наблюдаемой фактическую HTTP-доставку Sender после отдельного решения о составе backend snapshot и UI-представлении.

## Планируемые агрегаты

- `Send TPS` — все попытки отправки транзакций.
- `Accepted TPS` — транзакции, подтверждённые приёмником.
- `Retry TPS` — повторные попытки.
- `Failed TPS` — транзакции с окончательным отказом доставки.
- `In-flight` — выполняющиеся HTTP-запросы.
- `Backoff` — воркеры, ожидающие повторной попытки.
- Распределение ответов по классам: `2xx`, `4xx`, `5xx`, `network error`.

## Представление

- На pipeline-схеме: `Send TPS`, `Accepted TPS` и цветная строка состояний worker pool.
- В Inspector: остальные агрегаты и распределение HTTP-результатов.
- Не добавлять «последний HTTP response» ни для всего пула, ни для отдельного воркера: при параллельных воркерах это не даёт полезного диагностического вывода.

## Граница

Этот план не реализует новые метрики и не меняет текущий snapshot. К нему возвращаемся, когда потребуется полноценная наблюдаемость доставки.
