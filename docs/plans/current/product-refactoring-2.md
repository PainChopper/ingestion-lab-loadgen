# План реализации рефакторинга ingestion-lab — второй этап

Создан: 2026-10-05.
Статус: пункты 1–3 определены для реализации; реализация по этому плану не выполнена.

Продолжение [предыдущего плана](product-refactoring.md). Новые пункты добавляются
по мере совместного разбора текущего кода. Ниже зафиксированы конкретные изменения
и проверки для исполнителя.

## 1. Убрать обёртку lifecycle и хранить runState непосредственно

### Причина и итог

В [lifecycle.go](../../../loadgen/lifecycle.go) структура `lifecycle` содержит
единственное поле `state runState`. Конструктор `newLifecycle` только устанавливает
`runStateIdle`. Обёртка и отдельный указатель увеличивают путь доступа к состоянию
(`state.run.lifecycle.state`), а правила переходов могут быть методами самого
`runState`.

После изменения `controlRunState` хранит `state runState` по значению. Все шесть
методов переходов принадлежат `*runState`. Обёртка `lifecycle` и её конструктор
удаляются.

### Имена и размещение

- Сохранить имя типа `runState` и имена констант `runStateIdle`, `runStateRunning`,
  `runStatePaused`, `runStateFaulted`, `runStateResetting`: они описывают состояние
  прогона и уже используются в управлении и снимке статуса.
- Переименовать `loadgen/lifecycle.go` в `loadgen/run_state.go`:
  в нём оставить тип, константы и методы переходов.
- Переименовать `loadgen/lifecycle_test.go` в `loadgen/run_state_test.go`;
  адаптировать имена тестов и локальных переменных к удалению `lifecycle`.
- Поле внутри `controlRunState` назвать `state`. Чтение состояния становится
  `state.run.state`, переход — например, `state.run.state.pause()`.

### Реализация и владелец состояния

1. В [control_state.go](../../../loadgen/control_state.go) заменить поле
   `lifecycle *lifecycle` на `state runState`.
2. В `newControlState` явно инициализировать
   `run: controlRunState{state: runStateIdle}`. Нулевое значение строкового типа
   — `""`, поэтому удаление конструктора не отменяет инициализацию начального
   состояния. Не вводить новый конструктор для присваивания этой константы.
3. Перенести `run`, `pause`, `reset`, `fault`, `faultStart`, `completeReset`
   на получатель `*runState`: читать `*state`, присваивать новое значение в `*state`.
   Сохранить результаты `bool` и условия переходов.
4. Заменить чтения и вызовы в управляющем коде и существующих тестах.
   Переходы вызывать на поле владельца, а не на локальной копии состояния;
   локальные копии для чтения и построения снимка допустимы.
5. Сохранить владение изменяемым состоянием у `controlState` и выполнение
   рабочих переходов в его цикле событий. Новая форма хранения не требует
   дополнительной горутины, блокировки, общего состояния или геттера.
6. Удалить тип `lifecycle`, `newLifecycle` и ссылки на них в коде и тестах.

### Сохраняемые переходы

| Метод | Допустимое исходное состояние | Новое состояние |
|---|---|---|
| `run` | `idle`, `paused` | `running` |
| `pause` | `running` | `paused` |
| `reset` | `paused`, `faulted` | `resetting` |
| `fault` | `running`, `paused` | `faulted` |
| `faultStart` | `idle` | `faulted` |
| `completeReset` | `resetting` | `idle` |

Допустимый переход возвращает `true`. Для остальных исходных состояний метод
возвращает `false` и сохраняет прежнее значение. Повторные команды и ошибки
запуска должны обрабатываться так же, как до изменения.

### Внешнее поведение

Сохранить `type runState string` и строковые значения `idle`, `running`, `paused`,
`faulted`, `resetting`. В [runtime_status.go](../../../loadgen/runtime_status.go)
поле `runtimeRunStatus.State` уже имеет этот тип и тег `json:"state"`;
снимок сериализуется непосредственно. Имена и значения состояний в JSON,
HTTP-ответы и отображение UI остаются прежними.

Этот пункт меняет форму хранения и размещение кода. Он не меняет поведение
Run/Pause/Resume/Reset, остановку ресурсов или обработку сбоя Reader.

### Рекомендации по тестам и проверки исполнителя

- Адаптировать существующие тесты переходов в `run_state_test.go` к значениям
  `runState`. Удалить вспомогательные обёртки, которые нужны только старому типу;
  не переносить прежнюю структуру в тестовый код.
- Проверку начального `idle` выполнять через реальный `newControlState`
  в `control_state_test.go`. Тест, который сам присваивает `runStateIdle`
  и затем сравнивает его с той же константой, не нужен.
- Обновить прямую подготовку состояний в `event_loop_test.go`. Сохранить проверки
  команд, отказов в переходе, ошибки запуска и сбоя Reader, а также снимка статуса.
  Новые тесты добавлять только для конкретного непокрытого поведения.
- Применить `gofmt` к изменённым Go-файлам и выполнить существующий набор
  `go test ./...` из модуля `loadgen`. Результат выполнения записать при реализации;
  при подготовке этого плана тесты не запускались.
- Проверить поиском по Go-коду модуля, что объявлений и обращений к `lifecycle`
  и `newLifecycle` больше нет; просмотреть итоговый diff на пропущенные вызовы.

Пункт завершён, когда обёртка и конструктор удалены, новые файлы содержат тип
и его тесты, начальное состояние задаётся владельцем явно, переходы и JSON-статус
сохранены, а проверки исполнителя прошли.

## 2. Вынести адрес HTTP-сервера в конфиг

### Причина и итог

В [http_server.go](../../../loadgen/http_server.go) адрес прослушивания
`127.0.0.1:8080` задан непосредственно в `http.Server`. Для смены порта при конфликте
или запуска нескольких экземпляров сейчас требуется изменение кода.

Добавить в конфиг адрес HTTP-сервера:

```toml
[http]
addr = "127.0.0.1:8080"
```

Это адрес прослушивания `host:port`. Схема `http://` и путь в этом поле не нужны.
Настройка читается при запуске сервиса; изменение требует перезапуска.

### Реализация

1. В [config.go](../../../loadgen/config.go) добавить `HTTP httpConfig`
   с тегом `mapstructure:"http"` и тип `httpConfig` с полем
   `Addr string` и тегом `mapstructure:"addr"`.
2. Сделать `http.addr` обязательным в соответствии с существующим строгим
   декодированием конфига. Проверять непустой host и числовой порт 1–65535
   в формате `host:port`, включая адрес IPv6 в квадратных скобках.
   Использовать стандартный разбор адреса; сетевое разрешение имени при
   валидации не требуется. Ошибка указывает на поле `http.addr`.
3. В [config.toml](../../../loadgen/config.toml) добавить секцию `[http]`
   с прежним адресом `127.0.0.1:8080`.
4. В `startHTTPServer` задать `Addr: config.HTTP.Addr`. Конфиг уже передаётся
   в эту функцию, поэтому дополнительные параметры и новая обёртка не нужны.
   Сохранить существующие запуск, остановку, возврат ошибки `net.Listen`
   и логирование адреса сервера.
5. Обновить конфигурационные фикстуры, которые загружаются строгим декодером,
   и [документацию конфигурации](../../configuration.md).

### Связанные адреса

Адрес прослушивания сервера и адрес подключения клиента задаются отдельно.
Remote CLI уже принимает `--url`; его прежний адрес по умолчанию остаётся
`http://127.0.0.1:8080`. При выборе другого порта документировать пример
`snapshot --url http://127.0.0.1:8081` для сервера на `127.0.0.1:8081`.
Remote CLI не должен загружать серверный конфиг ради определения URL.

`sender.api.url` остаётся самостоятельным адресом назначения нагрузки.
Для текущего стенда Sender направляет запросы на встроенный ресивер; при смене
порта соответствующий URL также явно меняется в конфиге. Маршрут ресивера берётся
из этого URL по пункту 3. Автоматически выводить клиентские URL из адреса
прослушивания не требуется.

### Проверки исполнителя

- Проверить загрузку `http.addr`, отказ при отсутствующем поле, пустом или
  некорректном адресе и порте вне указанного диапазона.
- Проверить, что `startHTTPServer` действительно слушает настроенный адрес:
  использовать свободный локальный порт и выполнить запрос к существующему
  endpoint. Завершить сервер штатно; тест не должен зависеть от свободного 8080.
- Проверить, что ошибка занятого адреса возвращается вызывающему коду.
- Применить `gofmt` к изменённым Go-файлам и выполнить `go test ./...`
  из модуля `loadgen`. Эти проверки выполняются при реализации пункта.

Пункт завершён, когда сервер использует `http.addr`, пример конфига сохраняет
прежний адрес, запуск на другом порту проверен, а документация объясняет настройку
сервера и соответствующих клиентских адресов.

## 3. Брать маршрут встроенного ресивера из sender.api.url

### Причина и итог

В [http_server.go](../../../loadgen/http_server.go) встроенный фейковый ресивер
регистрируется по `internalTestIngestPath`, независимо от `sender.api.url`.
В конфиге тот же путь `/internal/test/ingest` записан второй раз как часть URL.
Изменение пути в конфиге меняет адрес отправки, но оставляет прежний маршрут
приёма, поэтому текущий локальный стенд перестаёт принимать нагрузку.

Решение владельца: пока Sender направлен на встроенный ресивер, использовать
`sender.api.url` как единый источник его маршрута. Удалить константу
`internalTestIngestPath`; отдельную настройку пути или переключатель ресиверов
не добавлять. Встроенный обработчик сохраняется.

### Реализация

1. Разобрать `config.Sender.API.URL` через `net/url` и использовать его `Path`
   при регистрации `internalTestIngestHandler` в `newServeMux`.
   Полный URL нельзя передавать в `mux.Handle`: маршруту нужен только путь.
   Для URL без пути использовать `/`, как при HTTP-запросе к корню сервера.
2. Сохранить отправку Sender по полному URL из конфига, включая адрес назначения
   и query-параметры. Параметры запроса не включать в шаблон маршрута.
3. Ошибку разбора URL передавать как ошибку запуска с указанием `sender.api.url`;
   не игнорировать её и не возвращать прежний путь как запасное значение.
   При конфликте пути со служебными маршрутами вернуть ошибку настройки
   до запуска сервера, сохранив существующие API, метрики и developer routes.
4. Удалить объявление `internalTestIngestPath` и все ссылки на него.
   В тестах самого handler можно использовать локальный адрес запроса:
   они проверяют обработку HTTP/JSON, а не регистрацию рабочего маршрута.
5. Обновить тесты регистрации mux и документацию: путь встроенного ресивера
   меняется через `sender.api.url` при запуске. Пример конфига может сохранить
   прежнее значение `/internal/test/ingest` как выбранный маршрут стенда.

Адрес прослушивания остаётся `http.addr` из пункта 2. Host и порт URL Sender
не задают адрес серверу автоматически; для локального стенда они должны вести
к его доступному адресу. Этот пункт сохраняет текущий встроенный ресивер
и не запускает работы по переходу на отдельный модуль `receiver`.

### Проверки исполнителя

- Задать в конфиге другой путь, например `/test/receive`, построить рабочий mux
  и отправить туда корректный POST: встроенный обработчик отвечает `204`.
- Для этого конфига прежний `/internal/test/ingest` больше не обслуживается
  фейковым ресивером и возвращает `404`.
- Проверить, что Sender отправляет по настроенному URL и запрос достигает
  обработчика mux с тем же путём. Использовать `httptest`, без обязательного 8080.
- Проверить URL без пути, URL с query-параметрами и отказ при конфликте
  со служебным маршрутом. Сохранить существующие тесты самого ingest handler.
- Проверить поиском отсутствие `internalTestIngestPath` в Go-коде,
  применить `gofmt` и выполнить `go test ./...` из модуля `loadgen`.
  При подготовке плана эти проверки не запускались.

Пункт завершён, когда константа удалена, путь приёма задаётся существующим
`sender.api.url`, изменение пути работает для отправителя и встроенного ресивера,
а проверки исполнителя прошли.
