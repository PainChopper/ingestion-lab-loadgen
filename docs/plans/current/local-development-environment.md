# Среда разработки и локальный инфраструктурный стенд

## Контекст

Следующий ingestion-контур потребует локально запускать Docker-сервисы: MinIO,
Postgres и Kafka. Сейчас checkout расположен на Windows-диске `D:`. Известно,
что запуск работы из WSL против этого checkout вызывает проблемы доступа к
файлам. Поэтому вариант «код на `D:`, а работа из WSL через `/mnt/d`» нельзя
считать надёжной базой.

Нужно осознанно выбрать одну из двух полноценных рабочих сред:

1. Windows: checkout на `D:`, GoLand, Go, Git for Windows и Docker-команды
   запускаются нативно в Windows. Скрипты и команды выполняются через
   PowerShell; Git Bash не используется.
2. WSL: checkout переносится в файловую систему WSL; Git, Go, Docker/Compose
   и tooling запускаются там, а IDE подключается к WSL-toolchain.

В Windows-варианте Git for Windows используется только из PowerShell. Git Bash
не является поддерживаемой средой. В WSL-варианте Git запускается внутри WSL и
только против checkout в файловой системе WSL; переход из WSL к checkout на
`D:` не допускается.

Решение влияет на разработку loadgen, будущего receiver и локального
инфраструктурного стенда, поэтому его нельзя принимать по удобству одной
команды или догадке.

## Цель

Выбрать и зафиксировать надёжную среду разработки для проекта, в которой
корректно работают checkout, Git, GoLand, Go toolchain, Docker Desktop/Compose
и будущие MinIO/Postgres/Kafka volumes. После решения подготовить минимально
воспроизводимый способ запуска локального стенда.

## Границы

- Не использовать WSL для работы с checkout на `D:` как постоянный вариант:
  этот путь уже проявил проблему доступа.
- Не использовать Git Bash.
- Не переносить checkout и не менять настройки Docker Desktop до подтверждённой
  рекомендации аналитика и решения владельца.
- Не реализовывать ingestion receiver и не поднимать Kafka/Postgres/MinIO в
  рамках анализа среды.
- Не создавать второй checkout «на всякий случай» без правила, какой из них
  является единственным рабочим источником.

## Этапы

1. [ ] Инвентаризировать текущую Windows-среду: версии Go, Git, GoLand и Docker
   Desktop, фактический Docker backend, расположение Docker data и доступное
   пространство на `D:`. Зафиксировать уже воспроизведённую проблему WSL →
   `D:` и её точный эффект.
2. [ ] Провести сравнительный анализ двух вариантов: нативная Windows-среда
   против полноценной WSL-среды с checkout внутри WSL. Проверить PowerShell +
   Git for Windows как единственный Windows-вариант и исключить Git Bash.
   Оценить скорость I/O,
   доступ к Docker, Git, GoLand, отладку, пути/права, background-процессы,
   хранение volumes и уборку временных артефактов.
3. [ ] Сформировать рекомендацию с явными компромиссами и критериями выбора.
   Если рекомендуются WSL, описать безопасную однократную миграцию checkout и
   IDE-toolchain; если Windows — описать нативный запуск Docker/Compose без
   обращения WSL к проектным файлам.
4. [ ] После одобрения владельцем применить выбранную среду и проверить
   минимальный smoke: clone/status Git, `go test`, GoLand indexing/debugging и
   запуск пустого Docker Compose-проекта без фоновых утечек.
5. [ ] Для выбранной среды зафиксировать расположение данных локального
   ingestion-стенда: отдельный каталог/volume на `D:`, предельный бюджет
   хранилища 400 ГБ, измерение фактического использования и явная процедура
   очистки. Не резервировать 400 ГБ заранее.

## Критерии приёмки

- Выбран ровно один поддерживаемый способ локальной разработки; вариант WSL
  против checkout на `D:` исключён из инструкции.
- Решение опирается на проверяемые наблюдения, а не только на предпочтение.
- Git из PowerShell на Windows либо Git внутри WSL, Go toolchain, GoLand и
  Docker/Compose работают из выбранной среды без
  расхождения путей и доступа.
- Docker data и будущие MinIO/Kafka/Postgres volumes не могут незаметно занять
  системный диск; для стенда определён лимит в 400 ГБ и измеримый usage.
- Инструкция позволяет другому разработчику воспроизвести окружение и удалить
  локальные инфраструктурные данные без затрагивания исходного checkout.
