# Отдельный HTTP receiver для ingestion-контура

## Контекст

Сейчас Sender по умолчанию отправляет batch в `/internal/test/ingest` того же
процесса loadgen. Этот endpoint нужен как лёгкая тестовая заглушка: он
проверяет HTTP/JSON-вход, читает тело и отвечает `204 No Content`, но не
является самостоятельной принимающей системой. Поэтому по loadgen нельзя
проверить сквозную доставку в отдельный сервис, его наблюдаемость и поведение
Sender при реальных задержках или ошибках приёмника.

Визуальный план будущего ingestion-контура уже закрепляет первый реальный
внутренний блок как Go HTTP receiver. Этот план реализует именно его минимальную
работающую версию, не обещая S3, Postgres outbox или Kafka.

## Цель

Добавить в репозиторий отдельный исполняемый Go-модуль `ingestion-lab-sink`:
HTTP-приёмник batch-ей, который loadgen запускает и нагружает как независимый
процесс. Receiver корректно принимает batch, публикует наблюдаемое состояние и
позволяет воспроизводимо проверить нормальную доставку, задержки и ошибки.

## Границы

- Receiver — отдельный HTTP-процесс с собственной конфигурацией и lifecycle,
  а не новый handler внутри loadgen.
- В первом этапе успешный batch не сохраняется: после валидации он учитывается
  в агрегатах и подтверждается ответом `204 No Content`.
- Не добавлять S3, базу данных, outbox, Kafka, авторизацию, Docker или UI.
- Не менять семантику Sender retry: receiver только выдаёт HTTP-результат,
  который Sender уже умеет интерпретировать.
- Встроенный `/internal/test/ingest` можно оставить для изолированных unit-тестов,
  но он не является основным стендом сквозной нагрузки.

## Этапы

1. [ ] Провести короткий анализ контракта Sender: точная JSON-модель batch,
   лимиты тела, статусы, которые означают success, terminal failure и retry.
   Зафиксировать пакетную структуру нового модуля и его TOML-конфигурацию.
2. [ ] Реализовать отдельную команду receiver: startup/shutdown, `POST` endpoint,
   проверку метода и `Content-Type`, ограничение тела и валидацию JSON. На
   корректный batch отвечать `204 No Content`; ошибки запроса выдавать
   детерминированно и без записи body в логи.
3. [ ] Добавить наблюдаемость receiver: счётчики принятых batch и транзакций,
   время последнего успешного batch, компактный status endpoint и Prometheus
   метрики. Lifecycle и ошибки логировать агрегированно; не логировать каждый
   успешный batch или транзакцию.
4. [ ] Добавить конфигурируемые режимы стенда: ответная задержка и заданный
   HTTP-ответ. По умолчанию режим normal; параметры должны быть явно отделены
   от production-семантики будущего ingestion service.
5. [ ] Добавить интеграционные проверки двух процессов: loadgen направляет
   Sender в receiver, normal delivery сходится по счётчикам, а delay и ошибка
   воспроизводимо показывают retry/backpressure. Процессы завершаются по
   deadline и не остаются после теста.
6. [ ] Провести независимое review и ручной smoke: запустить оба процесса,
   пройти `run → pause → resume → stop`, проверить status/метрики receiver и
   отсутствие фоновых процессов после остановки.

## Критерии приёмки

- Receiver стартует независимо от loadgen и получает batch по заданному URL.
- Корректный batch получает `204 No Content`; метод, тип содержимого, слишком
  большое тело и повреждённый JSON получают предусмотренную HTTP-ошибку.
- Status и метрики receiver показывают batch/transaction aggregates без
  логирования горячего успешного пути.
- Нормальный, delayed и error-сценарии можно воспроизвести конфигурацией.
- Сквозной тест подтверждает соответствие принимающего и отправляющего
  контуров с учётом in-flight/retry семантики.
- План не добавляет durable storage и не подменяет будущий ingestion service
  фиктивной телеметрией.
