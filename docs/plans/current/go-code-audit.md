## Поведение, которое закрепляет план

**Доставка.** `serve` → `runServe` → открытие HTTP → асинхронный glob → `startPipeline`. Пока идёт обнаружение, snapshot уже доступен в `starting`. Reader циклически занимает файлы под мьютексом и отправляет полные батчи и остаток каждого файла. Троттлер применяет TPS или bypass и передаёт батч в sender-очередь. Сегодня `runIntake` сначала учитывает получение батча, затем назначает его воркеру. Sender делает JSON POST. Receiver проверяет запрос, применяет lab-режим и увеличивает агрегаты перед ответом `204`. Sender учитывает подтверждение после получения успешного ответа; `run.totalTransactions` обновляется при сборе подтверждений на тике и при завершении. При потере ответа возможен повторный приём запроса. [Пайплайн](https://github.com/PainChopper/ingestion-lab-loadgen/blob/900546b/loadgen/pipeline_runtime.go#L18) · [Sender](https://github.com/PainChopper/ingestion-lab-loadgen/blob/900546b/loadgen/sender_pool.go#L182) · [Receiver](https://github.com/PainChopper/ingestion-lab-loadgen/blob/900546b/receiver/internal/receiver/server.go#L83)

**Управление и остановка.** CLI и frontend отправляют `{action,value}` в `/api/loadgen/commands`. В состоянии `running` event loop применяет настройку к пулу или троттлеру и возвращает пустой `200`. CLI подтверждает значение отдельным GET. Snapshot различает заданное число воркеров, живых и уходящих. При первом сигнале LoadGen переходит в `stopping`, продолжает отдавать snapshot и отвечает `409` на валидные команды. `stopReading()` останавливает новое чтение. Уже прочитанный остаток проходит вниз, очереди закрываются после выхода их производителей. По дедлайну отменяются HTTP и backoff, event loop собирает доступные подтверждения и пишет `partial`, не дожидаясь зависшей файловой операции. Receiver отдельно выполняет `Shutdown` в пределах `shutdown_timeout_ms`, при ошибке вызывает `Close`. [Event loop](https://github.com/PainChopper/ingestion-lab-loadgen/blob/900546b/loadgen/control_state.go#L66) · [Тесты остановки](https://github.com/PainChopper/ingestion-lab-loadgen/blob/900546b/loadgen/event_loop_test.go#L39) · [Остановка Receiver](https://github.com/PainChopper/ingestion-lab-loadgen/blob/900546b/receiver/cmd/receiver/main.go#L36)

## Этапы

Для каждого изменения поведения — адресная регрессия с наблюдаемым результатом до и после исправления. Общая приёмка этапа с Go-изменениями — `go vet ./...`, `go test ./...` и `go test -race ./...` в затронутом модуле. Замер пропускной способности D3 выполняется отдельно без `-race`.

### 1. Исправить дефекты в существующей архитектуре

**ID:** D12, D1, D2, D3, D5, D7, часть A2 и T4. **Зависимостей нет.** Компоненты — текущий sender-диспетчер, HTTP-клиент, троттлер, телеметрия очереди, обработка сигналов обоих бинарников.

- **D12 — первым исправить потерю принятого батча.** Сохранить приоритет уже назначенной работы. Решение воркера выйти и удаление из `workers` выполнить под одним захватом мьютекса. В тесте удерживать A, дать второму воркеру B, выполнить `2→1`, завершить B и задержать выход воркера. Затем `1→2`, подать C и дать диспетчеру завершить назначение при удерживаемом A. Одного `receivedBatchesTotal == 3` для синхронизации недостаточно: счётчик растёт до назначения. После снятия барьеров закрыть вход и дождаться штатного `pool.done`. Исправный получатель должен получить **A, B и C ровно по одному разу**. Проверить рост до решения уйти и после удаления воркера.
- **D1 — ограничить реактивацию числом `desired-active`.** Сначала возвращать живых воркеров вне backoff, затем находящихся в backoff, затем создавать недостающих. Тест удерживает три занятых воркера при `3→1→2`. До освобождения ожидаются `liveWorkers=3`, `drainingWorkers=1`, активных ровно два. После ухода лишнего остаются два живых. Существующий `2→1→2` сохранить.
- **D2 — выделить HTTP-клиент Sender.** У клона транспорта установить `MaxIdleConnsPerHost` и `MaxConnsPerHost` по `sender.workers.max`, ограничить дочитывание тела ответа. Ввести обязательный startup-only `sender.api.timeout_ms`, в поставляемом `loadgen/config.toml` — `30000`, версия схемы — 3. При загрузке, **до умножения на `time.Millisecond`**, проверить `1 ≤ timeout_ms ≤ math.MaxInt64 / int64(time.Millisecond)`. Тесты загрузки принимают обе границы и отвергают пропуск, ноль, отрицательное значение, максимум плюс один и старую схему. Отдельный тест с молчащим получателем подтверждает завершение попытки по таймауту и переход в backoff.
- **Регрессия транспорта D2.** К одному локальному HTTP/1.1-серверу отправить две последовательные волны по `N=4` параллельных запроса через один клиент Sender. В каждой волне сервер удерживает ответы, пока в обработчик не войдут все четыре запроса. Клиент полностью читает и закрывает все ответы первой волны до запуска второй. Через `ConnState(StateNew)` зафиксировать четыре соединения после первой волны и **ноль новых соединений во второй**. Ожидание барьера ограничить дедлайном теста. Старый `DefaultClient` сохраняет между волнами максимум два idle-соединения к хосту и вынужден открыть новые. Последовательное обслуживание через одно соединение не пройдёт барьер.
- **D3, D5, A2, T4 — исправить расписание троттлера.** Первый батч ждёт полный интервал. Кредит после простоя входа ограничен одним интервалом, после блокировки выхода якорь переносится на момент передачи. Смена TPS пересчитывает дедлайн от начала того же слота. Блокировка закрывается по своему ID. В `synctest` проверить первый интервал, полный выход, длинный простой входа, выход из TPS=0 и смену `200000→400000` у уже отждавшего батча. После освобождения выхода этот батч передаётся сразу. Короткий замер D3 по методике Astra на Windows — постоянно полный вход, свободный выход, одна секунда, батч 1000, цель 2 млн TPS, результат **не ниже 95%**.
- **D7 — восстановить стандартную обработку сигнала после первого Ctrl+C.** Для каждого бинарника отдельно задержать завершение, подать первый сигнал, зафиксировать начало штатной остановки и подать второй. Процесс должен завершиться до истечения удерживаемого grace.

### 5. Переписать Sender и Reader на модель с флагом ухода и `wake`

**ID:** A3, A8, D4, D6, T5. **Зависимость:** этап 4. Sender-воркеры читают общую очередь напрямую. Reader занимает файл под мьютексом. В обоих пулах проверка ухода и удаление воркера атомарны. Рост реактивирует живых уходящих до `desired`; после начала остановки новые воркеры не создаются.

- **Регрессия D4 — переход от свободного воркера к его уходу.** Запустить два воркера. Первый держит A, второй свободен. На старой реализации синхронизироваться с моментом, когда intake уже прошёл проверку доступности и ждёт вход. Уменьшить пул до одного, подать B в буферизованную очередь и удерживать A. Дать всем готовым горутинам дойти до устойчивого состояния. Старый код снимает B, увеличивает счётчик получения, но попытки доставки B нет и единственный оставшийся воркер занят A. Зафиксировать это сочетание, чтобы тест отличал скрытый батч от обычного ожидания.
- **Критерий новой модели D4.** В той же устойчивой точке B либо остаётся в очереди и ещё не учтён как полученный, либо принят конкретным воркером. Владение проверять по ID батча у управляемого получателя и состоянию соответствующего воркера. После освобождения A закрыть вход, дождаться штатного drain и проверить ровно одну доставку B. Второй вариант теста выпускает подачу B и уменьшение пула с общего барьера. Допустимы оба порядка, а критерии владения и итоговой доставки одинаковы. Отдельно сохранить **`TestSenderPoolBackpressureWhenAllWorkersRetry`** для случая, когда до появления следующего батча уже заняты все воркеры.
- **Sender, граница resize.** Сохранить тесты D1 и D12 из этапа 1. При уменьшении сразу на нескольких воркеров различать воркеры и батчи: каждый уходящий может принять максимум один новый батч, показать его как draining in-flight и доставить. Для D6 удержать фактический выход воркера и получить возврат `reconcile` и ответ snapshot до снятия барьера. Проверить сохранение текущего backoff при resize и закрытие `pool.done` при отмене родительского контекста с открытым входом.
- **Reader, граница остановки.** Сохранить приоритет ухода свободных, завершение текущего файла при downscale и реактивацию заблокированного воркера без дубля. Вызвать только `stopReading()` при живом контексте и проверить доставку остатка и закрытие `done`. Для потерянного пробуждения использовать один файл и W0/W1/W2: после освобождения файла и ухода W0/W1 оставшийся W2 начинает чтение без следующей команды. При освобождении файла будить всех свободных неуходящих воркеров.

**Готовность.** Обе версии перехода D4, исходный тест backpressure, неизменные поведенческие критерии D1/D12 и проверки Reader проходят под `-race`. Удерживаемый выход воркера не задерживает event loop.

### 9. Перевести Receiver на схему 2

**ID:** D8, D9, D11, I1, I6, I7, I15, T1, T4 в Receiver. **Зависимости:** самостоятельный этап. Обновить `receiver/config.toml`, перевести конфиг на Viper, подключить `slog` с уровнем из конфига. Сохранить точный маршрут из `ingest.path`. Код уже регистрирует этот путь; исправление D9 требуется в валидации, которая сегодня разрешает только `/internal/ingest`.

- В файловой структуре оставить **`ResponseStatus *int`**. Установить `UnmarshalExact`, `WeaklyTypedInput=false`, **`ErrorUnset=true` и `AllowUnsetPointer=true`**. Единственное необязательное поле-указатель — `lab.response_status`. Табличный тест проверяет три исхода: отсутствие → `204`, явный `204` → принят, явный `0` → ошибка.
- Проверить дробное значение на реальном ключе **`lab.response_delay_ms = 1.9`**. Оно даёт ошибку декодирования. Отдельно проверить отсутствие обязательного `lab.response_delay_ms`, неверный тип, неизвестный ключ и старую схему.
- Проверять точность маршрута до регистрации. Некорректный шаблон, `/status`, `/` и путь с завершающим `/` дают ошибку конфига. Для тела использовать `MaxBytesReader` и `ReadAll` перед `json.Unmarshal`. Декодировать `[]transaction`, отвергать элемент `null`, сохранить приём `[{}]` по решению владельца.

**Готовность.** Тесты handler подтверждают приоритет `413` над `400` для слишком большого JSON, `HEAD/405`, счётчики только при успешном приёме, задержку и её отмену на виртуальном времени. Тесты конфига различают все три состояния `ResponseStatus`.

**Сравнимость с T8270.** Runtime overlay добавляет только измерительный тест к настоящему `loadgen/internal/pipeline`; неизменённый `startThrottler` вызывается с `Rate{TPS: 2_000_000, Installed: true}`. На каждое окно создаются новые stage, контекст и очереди: вход заранее наполнен 8192 батчами по 1000, выход имеет буфер 16; единственный потребитель непрерывно забирает батчи. Как в [исходном стенде T8270][M0], `time.Now()` и таймер на 1s создаются до запуска stage; считаются только полученные потребителем транзакции, `time.Since(startedAt)` снимается при выборе ветки таймера, затем выполняются cancel и ожидание `stage.done`. Drain после окна не добавляется к числителю или elapsed. Изменение конструкции очередей и вызова запуска соответствует переносу в `internal/pipeline`; расписание stage не подменяется. HTTP, Reader и Sender в этом замере не участвуют.

**Арифметика.** Доля = `100 × transactions × 1e9 / (2_000_000 × elapsed_ns)`; знаменатель содержит фактическое монотонное время, а не номинальную секунду. Решение PASS принимается до округления: `100 * transactions * 1_000_000_000 >= 95 * 2_000_000 * elapsed_ns`. Целочисленные произведения укладываются в `int64` при наблюдавшихся значениях; стенд проверяет границы, а отдельный пересчёт всех 15 строк использует `BigInteger` и десятичную арифметику. После остановки каждого stage проверены равенства: транзакции = полученные батчи ×1000; отправленные батчи = полученные в окне + остаток выхода; прочитанные батчи = 8192 − остаток входа. Число прочитанных батчей равно отправленным либо на один больше из-за отменённого in-flight батча. Все проверки счётчиков прошли; вход ни разу не исчерпан.
