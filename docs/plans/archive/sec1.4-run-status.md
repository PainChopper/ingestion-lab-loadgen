# SEC1.4 — состояние запуска в UI

Статус: реализован. Go-проверки, 276 frontend-тестов, build/lint и проверка UI с backend прошли. По просьбе владельца итоговое ревью и дополнительная фиксация журналов не выполнялись.

## Контракт

- Работа выполняется в текущем checkout `ingestion-lab-loadgen`. Владелец явно разрешил для SEC1.4 расширение HTTP-контракта и необходимые изменения `frontend/`.
- `GET /api/loadgen/snapshot` сохраняет четыре существующих поля и всегда добавляет `elapsedMs` (неотрицательное целое число миллисекунд) и `startError` (непустая строка либо `null`).
- Время принадлежит Go event loop: начинается только после успешной подготовки producer, растёт в `running`, фиксируется после остановки consumer при Pause, продолжается при Run и обнуляется при принятом Reset. Повторный Run в `running` не перезапускает часы или pipeline.
- Ошибка синхронной подготовки producer сохраняет `idle` и нулевое время. Она хранится в `startError` до успешного Run или принятого Reset; повторная неудачная попытка заменяет сообщение. Ошибки Reader после успешного старта относятся к SEC5.4.
- `POST /api/loadgen/commands` для Run ждёт результата владельца состояния. Успех и повторный Run возвращают прежний HTTP 200 без тела; ошибка старта — HTTP 422 с JSON `{"error":"причина"}`. Существующий Reset во время работы возвращает 409 без изменений состояния.
- UI backend-режима показывает значения snapshot без локального отсчёта времени. Рядом с управлением запуском выводится сообщение «Не удалось запустить: <причина>» с `role="alert"`. Ошибка запуска не превращается в ошибку соединения.
- HttpAdapter строго проверяет новые поля, сохраняет последнее подтверждённое состояние при сбое опроса и переносит причину HTTP 422 в CommandReceipt. Snapshot остаётся источником состояния UI; существующий опрос раз в секунду сохраняется.
- Общая frontend-модель получает `startError: string | null`; SimulationAdapter возвращает `null`. Новые transport/schema version, зависимости и глобальное состояние не вводятся.

## Исполнение

1. CODER backend — `gpt-5.6-sol`, `high`: Go, HTTP и релевантные Go-тесты.
2. CODER frontend — `gpt-5.6-terra`, `high`: HttpAdapter, модель, отображение и релевантные тесты.
3. TESTER — `gpt-5.6-terra`, `medium`: независимые проверки и локальный runtime smoke.
4. REVIEWER — `gpt-5.6-sol`, `high`: итоговый diff, корректность и идиоматичность Go.

Каждый этап получает отдельный тикет. Изменяющие роли выполняются последовательно. LEAD принимает полноту отчётов и ведёт runtime.

## Приёмка

- Idle показывает нулевое время; Run → Pause → Run → Reset даёт рост, остановку, продолжение и сброс времени.
- Повторный Run не создаёт новый producer и не обнуляет время; Reset в running сохраняет запуск и возвращает 409.
- Неудачный запуск возвращает 422 и сохраняет сообщение в snapshot; Reset и успешный retry очищают его.
- UI показывает время Go и причину старта, режим simulation сохраняет работоспособность.
- Go- и frontend-проверки и локальная связка UI/backend подтверждены независимым TESTER; REVIEWER не оставил препятствующих приёмке замечаний.

## Разрешённые проверки

Локальные тесты, build-артефакты и временные процессы на loopback для проверки UI/backend входят в согласованную проверку. Для успешного старта используется только синтетический Parquet в runtime, без production-данных, внешних отправок и изменения окружения. Состояние вне SEC1.4 не меняется.
