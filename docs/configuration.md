# Конфигурация loadgen

LoadGen читает один TOML-файл до запуска HTTP-сервера. Без аргументов используется `config.toml` из текущего рабочего каталога; другой файл задаётся через `loadgen serve --config <path>`. Прогон стартует автоматически один раз на процесс, останавливается Ctrl+C или SIGTERM.

Конфиг не версионируется. Строгий разбор отвергает лишние и недостающие ключи. При смене смысла, единиц или допустимых значений существующего ключа ключ переименовывается, например timeout_ms → timeout_s; старое имя после этого отвергается как постороннее. Это относится и к необязательным ключам.

Все ключи LoadGen из [примера](../loadgen/config.toml) обязательны. Имена секций и ключей чувствительны к регистру; неизвестные ключи и секции, включая пустые, запрещены. Строки и bool не преобразуются в числа; дробная часть, NaN и переполнение целочисленного поля дают ошибку, в том числе в `sender.retry.delays_ms`. Явные `0` и `false` сохраняются.

Обязательное `http.addr` — непустой host и числовой порт 1–65535 в формате `host:port`, для IPv6 — `[::1]:8080`. Схема и путь не указываются, DNS при проверке не вызывается. По умолчанию пример слушает `127.0.0.1:8080`; при изменении адреса передай его в CLI через `--url` и настрой Vite proxy.

`source.path` — glob-путь Parquet, абсолютный или относительный к рабочему каталогу сервера. Поставляемый `../data/MBD-mini/trx/fold=*/*.parquet` рассчитан на запуск из `loadgen/`; расположение файла конфигурации не меняет эту базу. `sender.api.url` — абсолютный HTTP(S) URL с host без fragment; пример отправляет на `http://127.0.0.1:8081/internal/ingest`. Для локального запуска сначала запусти Receiver из `receiver/` командой `go run .`, затем LoadGen.

Startup-настройки — скаляры: `reader.read_batch_size = 1000`, `readerChannel.capacity = 2`, `senderChannel.capacity = 0`. Batch size положительный, включая 1500; сохраняется технический предел безопасного умножения на `time.Second` (9 223 372 036 на 64-битной платформе). Capacity неотрицательная, включая 3; ноль означает unbuffered rendezvous. Проверяются представимость размера backing array и сама capacity: не более 9 007 199 254 740 991 (2^53−1) для точного представления целых в JSON. Произведение `capacity * read_batch_size` не ограничивается. Это не проверка доступной RAM.

`reader.workers` и `sender.workers` содержат только обязательные `initial` и `max`: начальное значение 1..max. Сервер задаёт min=1 и step=1. Max — операторский бюджет, а не фиксированный предел картинки. `sender.workers.max` также задаёт все три HTTP transport limit: MaxIdleConns, MaxIdleConnsPerHost, MaxConnsPerHost.

`throttler.requested_tps` содержит `initial` и `max`; min=0 задан сервером. Max положительный и не превышает 9 007 199 254 740 991 (2^53−1); initial и команды принимают любое целое в 0..max включительно. Это ограничение для точного представления целых в JSON ([RFC 8259 §6](https://www.rfc-editor.org/rfc/rfc8259#section-6)), а не предел производительности троттлера. Например, initial или команда 2000001 допустимы при max=4000000. Для workers и публикуемых числовых настроек также учитывается этот JSON-предел; это не рекомендация размера пула.

Шаг клапана выбирает UI: наименьшее число вида 1/2/5 × 10^k, не меньше 1, дающее не более 11 интервалов. Позиции идут от min с этим шагом и завершаются точным max. Последняя внутренняя позиция убирается, если до max меньше половины шага; ровно половина сохраняется, min остаётся всегда. Например, при max=4000000 шаг равен 500000, при max=250000 — 50000. Ручной ввод и отправка команды не требуют кратности шагу.

```toml
[throttler.requested_tps]
initial = 2000001
max = 4000000
```

`throttler.installed = true` — bool-скаляр: true включает TPS limit и удерживает поток при TPS=0; false включает bypass, сохраняя запрошенный TPS. Поля `unit`, `mutability`, `allowed`, worker min/step и TPS min в TOML не принимаются. Единицы и режим применения определены контрактом.

`sender.api.timeout_ms` — обязательный таймаут одной HTTP-попытки, включая чтение ответа: 1..9 223 372 036 854 мс, в примере 30000. `sender.retry.delays_ms` — непустой массив положительных неубывающих задержек в миллисекундах; последняя задержка повторяется до успеха или отмены. `sender.retry.jitter_percent` — 0..50, ноль отключает jitter. Длительности проверяются с учётом максимального положительного jitter. В примере задержки [250, 500, 1000, 2000, 5000], jitter=20. `logging.level` принимает debug/info/warn/error. Эти настройки применяются при старте; environment, KV override и hot reload отсутствуют.

`GET /api/loadgen/config` возвращает отдельный объект ровно из семи неизменяемых полей: `readerWorkersMax`, `senderWorkersMax`, `requestedTpsMax`, `readBatchSize`, `readerChannelCapacity`, `senderChannelCapacity`, `sourcePath`. Последнее поле содержит `source.path` как есть. Объект строится один раз при создании HTTP mux из уже загруженного TOML и не обращается в event loop. Ответ доступен, пока HTTP-сервер принимает запросы, в том числе в `starting`, `running`, `stopping` и `faulted`. `sender.api.url`, retry и другие настройки в этот объект не входят.

Snapshot `GET /api/loadgen/snapshot` содержит только живое состояние, без раздела `config`. Текущие `reader.workers`, `sender.workers`, `throttler.requestedTps` и `throttler.installed` остаются в snapshot; команды меняют их, не меняя config. Начальные `initial` остаются только в TOML. Каналы публикуют глубину в batch, без capacity и оценки транзакций. CLI берёт ёмкости из отдельного config и явно помечает `depthBatches × readBatchSize` как приближённую оценку: последний batch может быть неполным. CLI и HTTP frontend используют этот контракт; snapshot со старым разделом `config` отвергается строгим разбором. Simulation независима от TOML, сохраняет собственные настройки модели и отдаёт config отдельно через тот же интерфейс адаптера (`getConfig()`), с `sourcePath = 'simulation'`; её wire snapshot также не содержит config. При загруженном config UI показывает batch/capacity как числа; толщина шланга использует визуальную шкалу 1000..100000 tx, геометрия capacity — фактическую ёмкость.

HTTP-адаптер фронтенда запрашивает config при старте и опрашивает snapshot раз в секунду. Config перечитывается при уменьшении `capturedAtMs` и после восстановления успешного опроса snapshot вслед за неудачным. Второй признак учитывает рестарт, при котором новый процесс к следующему опросу работает дольше старого. При неудачном опросе и обнаружении рестарта старый config сбрасывается; запоздавший ответ config, начатый до этой границы, не применяется. Ошибка config не останавливает опрос snapshot: повторная попытка выполняется при следующем опросе, без отдельного таймера. Пока актуальный config не загружен, числовые контролы недоступны, ёмкости и размер батча равны `null`, все команды отклоняются как `unavailable`, а соединение показывается как `connecting` либо `error`, даже если сохранённый snapshot имеет состояние `running`.

`reader.sourceError` — null либо `operation`, `path`, `message`. Path — точная строка, переданная открытию файла; при ошибке glob — исходный шаблон. Нормализация, сокращение до имени и относительного пути не выполняются. Лог `reader_source_failed` пишет `path`, `runtime_summary` — `source_error_path`; поля ёмкостей `*_channel_capacity` берутся из config.

Сервер публикует только накопительные итоги: `reader.rowsRead`, `inputTransactionsTotal`/`outputTransactionsTotal` каждого канала, `blockedMs` и подтверждённые `run.totalTransactions`. Они не обнуляются в течение процесса. Корневой `capturedAtMs` — миллисекунды монотонных часов от единой точки при старте сервиса; перевод системного времени на него не влияет. Снимок использует одну метку времени, показатели читаются последовательно: при работающих воркерах возможен краткий рассинхрон разных счётчиков.

Клиент считает скорость по разности итогов и `capturedAtMs` двух снимков. Первый снимок, равное время или уменьшение времени/счётчика не дают скорости за интервал; новый снимок становится базой следующего расчёта. CLI `status` делает два GET-запроса: config и snapshot. Оба ответа разбираются строго: неизвестные поля и лишний JSON отвергаются; ошибка любого запроса завершает команду с указанием эндпоинта. Вид вывода status не меняется: он показывает явно подписанные средние TPS с начала прогона: итог / `run.elapsedMs`; до старта — ноль. Admitted берётся из входного итога Sender channel. Prometheus читает `loadgen_transactions_total` непосредственно при сборе, без тика; `loadgen_target_tps` остаётся установкой. `runtime_summary` по собственному минутному таймеру пишет накопительные итоги каналов. Отдельной настройки окна метрик нет; неизвестные TOML-таблицы отвергаются, в том числе пустые.

`reader.workerStates` и `sender.workerStates` — списки живых воркеров с полями `activity` и `draining`. У Reader активность `idle`/`reading`/`blocked`, у Sender — `idle`/`inFlight`/`backoff`. `blocked` сохраняет владение файлом, `backoff` — батчем; `draining` независимо запрещает следующую работу после завершения текущей. До запуска и при ошибке источника до старта оба списка равны `[]`. Порядок незначим, повторяющиеся состояния допустимы. `workers` остаётся заданной целью: при уменьшении пула длина списка временно больше цели. CLI вычисляет прежние счётчики из списков; `runtime_summary` сохраняет для каждого пула только цель и число живых воркеров.

CLI предоставляет `status` и четыре `set`: readers/senders/tps/throttle. Они принимают `--url <url>` (по умолчанию `http://127.0.0.1:8080`), абсолютный HTTP(S) адрес без userinfo/query/fragment/base path. HTTP actions: set-reader-workers, set-sender-workers, set-requested-tps, set-throttler-installed, например `{"action":"set-throttler-installed","value":false}`. Три числовых controls и installed доступны только во время running/connected; batch, capacity и startup-настройки не редактируются. HTTP/Target telemetry, которую сервер не предоставляет, остаётся недоступной.

HEAD config и snapshot возвращают заголовки соответствующего GET без тела. Неподдерживаемые методы: 405 с Allow GET, HEAD для config и snapshot или POST для commands. Успешная команда — пустой 200, отказ по состоянию прогона — пустой 409; неправильная команда — 400, тело более 4096 байт — 413 до JSON validation. Недоступный event loop или прерванное ожидание — 503 для snapshot/commands; отдельный config от event loop не зависит. Команда могла примениться, проверь новый snapshot. CLI `set` отправляет POST команды и подтверждает результат только через GET snapshot, не запрашивая config. Подтверждение требует явно присутствующего целевого поля, включая 0/false; ошибка подтверждения — exit 4.

## Конфигурация Receiver

Receiver читает TOML из `--config <path>`; без флага — `config.toml` из текущего каталога. Конфигурация для локального запуска находится в `receiver/config.toml`. Конфиг не версионируется и следует правилу переименования ключей выше. Все ключи обязательны, кроме `lab.response_status`. Имена секций и ключей чувствительны к регистру; неизвестные ключи и секции, включая пустые, отклоняются. `lab.response_delay_ms` задаётся явно, включая допустимый ноль. Строки и bool не преобразуются в числа, дробные значения целочисленных полей отклоняются.

`server.address` задаёт адрес HTTP-сервера, `server.shutdown_timeout_ms` — положительное целое число миллисекунд для штатного завершения активных запросов. По истечении срока соединения закрываются принудительно, процесс завершается с ошибкой. Для него и `lab.response_delay_ms` верхняя граница равна 9 223 372 036 854 мс; задержка может быть нулевой. `logging.level` принимает `debug`, `info`, `warn` или `error` и фильтрует структурированные сообщения запуска, остановки и ошибок; отдельных сообщений о каждом запросе или батче нет.

`ingest.path` задаёт точный абсолютный путь; стандартный маршрут — `/internal/ingest`, другой пример — `/v1/batches`. Формат: `^(/[A-Za-z0-9._~-]+)+$`. В непустом сегменте разрешены только ASCII-буквы `A-Z`, `a-z`, цифры `0-9` и символы `._~-`. Корень, завершающий слеш, повторные слеши, целые сегменты `.` и `..`, путь `/status`, Unicode, %-кодирование, символы `!$&'()*+,;=:@`, пробелы, управляющие символы, шаблоны `{...}`, query и fragment запрещены. Соседние пути и подпути не принимают батчи. Проверка одинакова для TOML и программного создания обработчика. Входящие URL обрабатываются стандартным `http.ServeMux`, дополнительной фильтрации нет.

Receiver принимает `POST` на настроенный путь с `Content-Type: application/json` и непустым JSON-массивом транзакций. `[{}]` допустим, `null`, `[null]` и пустой массив отклоняются. При корректном MIME тело больше `ingest.max_body_bytes` даёт 413 до проверки JSON; прочие ошибки тела дают 400. Необязательное `lab.response_status` допускает 204, 400 или 500: пропуск означает 204, явный 0 — ошибка конфигурации. Задержка действует перед выбранным ответом. Счётчики растут только при 204, отменённое ожидание и ответы с ошибкой их не меняют.

`GET /status` сохраняет прежнюю форму JSON со счётчиками и разделом `lab`. `HEAD /status` возвращает те же заголовки без тела. Неподдерживаемые методы получают стандартный 405 и `Allow: GET, HEAD` для status либо `Allow: POST` для ingest.
