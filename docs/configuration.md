# Конфигурация loadgen

Поле `initial` в TOML и `config.<настройка>.initial` в JSON задаёт загруженное начальное значение настройки до runtime override. Команда меняет текущее применённое значение, сохраняя `config.initial`; для `startup-only` настроек начальное значение действует весь срок службы процесса. Это поле обязательно, включая допустимый ноль capacity. Старое имя `default` больше не принимается ни отдельно, ни вместе с `initial`; совместимого alias нет.

LoadGen читает один TOML-файл до запуска HTTP-сервера. При запуске без аргументов используется `config.toml` из текущего рабочего каталога. Другой файл указывается через `loadgen serve --config <path>`. Прогон стартует автоматически и выполняется один раз на процесс. Для штатной остановки нажми Ctrl+C или отправь SIGTERM.

Поддерживается только `schema_version = 3`. Неизвестные и пропущенные ключи дают ошибку загрузки. Строки и bool не преобразуются в числа; число с дробной частью не принимается в целочисленном поле, включая элементы `sender.retry.delays_ms`. Явные `0` и `false` допустимы там, где это разрешает сама настройка.

Обязательное поле `http.addr` задаёт адрес прослушивания при запуске: непустой host и числовой порт 1–65535 в формате `host:port`; для IPv6 — `[::1]:8080`. Схема и путь здесь не указываются. Изменение требует перезапуска, DNS при проверке конфигурации не выполняется.

```toml
[http]
addr = "127.0.0.1:8080"
```

Если LoadGen слушает другой порт, например `127.0.0.1:8082`, передай его в remote CLI: `status --url http://127.0.0.1:8082`. Без флага CLI обращается к `http://127.0.0.1:8080`.

Поле `sender.api.url` задаёт адрес назначения Sender и проверяется при загрузке конфига. Нужен абсолютный HTTP(S) URL с хостом и без фрагмента. Sender использует указанный путь и query-параметры при отправке. В checked-in конфиге Sender отправляет батчи на `http://127.0.0.1:8081/internal/ingest`. Для локального запуска сначала запусти Receiver из каталога `receiver/` командой `go run ./cmd/receiver --config config.example.toml`, затем запусти LoadGen.

В схеме `schema_version = 3` поле `sender.api.timeout_ms` обязательно. Оно задаёт таймаут одной HTTP-попытки в миллисекундах, включая чтение ответа. Допустимо целое число от 1 до 9 223 372 036 854 включительно. В поставляемом конфиге задано 30 000 мс. Настройка применяется при запуске. Если попытка истекает по таймауту, Sender повторяет её по расписанию `sender.retry`.

Для чтения состояния есть CLI-команда `status`. JSON-снапшот доступен через HTTP `GET /api/loadgen/snapshot`. Во время прогона `set` принимает только `readers`, `senders`, `tps` и `throttle`. Все эти команды принимают необязательный `--url <url>`; по умолчанию используется `http://127.0.0.1:8080`. URL должен быть абсолютным HTTP(S) адресом без userinfo, query, fragment и базового пути.

`HEAD /api/loadgen/snapshot` возвращает заголовки GET без тела. Неподдерживаемые методы получают стандартный `405 Method Not Allowed`: `Allow: GET, HEAD` для snapshot и `Allow: POST` для commands. Успешная команда возвращает пустой 200, отклонённая по состоянию прогона — пустой 409. Ошибка команды даёт 400; тело более 4096 байт даёт 413 даже при некорректном JSON в начале. Недоступный event loop или прерванное ожидание ответа дают 503. После прерывания команда могла уже примениться; состояние нужно проверить новым snapshot. CLI подтверждает `set` по явно присутствующему целевому полю snapshot, включая допустимые 0/false; ошибка подтверждения возвращает exit 4.

Поддерживаются `[http]`, `[source]`, `[reader.read_batch_size]`, `[reader.workers]`, `[readerChannel.capacity]`, `[senderChannel.capacity]`, `[throttler.requested_tps]`, `[throttler.installed]`, `[sender.workers]`, `[sender.api]`, `[sender.retry]`, `[metrics.window_ms]` и `[logging]` из `config.toml`. `source.path` должен быть абсолютным glob-путём; unit и mutability обязательны. Конфигурация не принимает environment, KV overrides и не наблюдается для hot reload. Размер батча и ёмкости обеих очередей задаются при старте и действуют весь процесс. Для этих трёх настроек обязательно значение `startup-only` в TOML; оно же публикуется как `mutability` в JSON-снапшоте. Снапшот публикует настройки в поле `config`.

`reader.workers` и `sender.workers` задают собственные `initial`, `min`, `max` и `step`: `min >= 1`, `max >= min`, `step > 0`. Шаг отсчитывается от `min`; допустимы значения `min + k * step`, не превышающие `max`. Начальное значение должно принадлежать этой сетке. Для обоих диапазонов обязательны `unit = "workers"` и `mutability = "immediate"`. Профили из поставляемого конфига — примеры, а не фиксированные ограничения. Snapshot публикует загруженные диапазоны и начальные значения.

`sender.retry.jitter_percent` принимает целое значение от 0 до 50 включительно; 0 отключает разброс задержки. `delays_ms` — непустой массив положительных неубывающих задержек в миллисекундах. Загрузчик проверяет верхнюю границу каждой задержки с учётом максимального положительного jitter, чтобы длительность не переполнялась. Обе настройки применяются при запуске; в поставляемом примере jitter равен 20.

Настройка throttler использует bool: `[throttler.installed]`, `initial = true`, `allowed = [true, false]`, `mutability = "immediate"`. `true` включает ограничение TPS (при TPS=0 ожидает), `false` включает bypass, сохраняя запрошенный TPS. HTTP-команда: `{"action":"set-throttler-installed","value":false}`. CLI: `set throttle <true|false>`. Snapshot публикует `throttler.installed` и `config.throttlerInstalled` с булевыми initial/allowed; прежние строковые значения и имена не принимаются.

## Конфигурация Receiver

Receiver читает TOML из `--config <path>`; без флага — `config.toml` из текущего каталога. Пример находится в `receiver/config.example.toml`. Поддерживается только `schema_version = 2`: при миграции со схемы 1 обнови версию и явно задай `lab.response_delay_ms`, включая допустимый ноль. Все ключи обязательны, кроме `lab.response_status`; неизвестные ключи отклоняются. Строки и bool не преобразуются в числа, дробные значения целочисленных полей отклоняются.

`server.address` задаёт адрес HTTP-сервера, `server.shutdown_timeout_ms` — положительное целое число миллисекунд для штатного завершения активных запросов. По истечении срока соединения закрываются принудительно, процесс завершается с ошибкой. Для него и `lab.response_delay_ms` верхняя граница равна 9 223 372 036 854 мс; задержка может быть нулевой. `logging.level` принимает `debug`, `info`, `warn` или `error` и фильтрует структурированные сообщения запуска, остановки и ошибок; отдельных сообщений о каждом запросе или батче нет.

`ingest.path` задаёт точный абсолютный путь, например `/internal/ingest` или `/v1/batches`. Корень, завершающий слеш, повторные слеши, сегменты `.`/`..`, пробелы, управляющие символы, шаблоны `{...}`, query и fragment запрещены. Путь `/status` и его percent-encoded варианты зарезервированы. Соседние пути и подпути не принимают батчи. Percent-encoded сегменты проверяются до регистрации маршрута; закодированный слеш внутри сегмента остаётся частью этого сегмента.

Receiver принимает `POST` на настроенный путь с `Content-Type: application/json` и непустым JSON-массивом транзакций. `[{}]` допустим, `null`, `[null]` и пустой массив отклоняются. При корректном MIME тело больше `ingest.max_body_bytes` даёт 413 до проверки JSON; прочие ошибки тела дают 400. Необязательное `lab.response_status` допускает 204, 400 или 500: пропуск означает 204, явный 0 — ошибка конфигурации. Задержка действует перед выбранным ответом. Счётчики растут только при 204, отменённое ожидание и ответы с ошибкой их не меняют.

`GET /status` сохраняет прежнюю форму JSON со счётчиками и разделом `lab`. `HEAD /status` возвращает те же заголовки без тела. Неподдерживаемые методы получают стандартный 405 и `Allow: GET, HEAD` для status либо `Allow: POST` для ingest.
